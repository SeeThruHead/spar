Spar benchmarks

The same table app in Spar, Solid 1.9.19 (solid), Solid 2.0.3 (solid2), React 19.3.1, Foldkit 0.170.0 and Effect UI (snapshot 6f86af8), built with Vite and driven in headless Chromium 159.0.8154.6 on the CI box box-node-c39789b8fb7d970d (AMD EPYC 4585PX 16-Core Processor, 8 cores), with nothing else running on it. Each time is the median of 10 runs after 2 warm-up runs, from the click until the next frame after the page reached its final state, each click 100 ms after the steps that set it up. Lower is better in every chart.

How it is measured: each run loads the app fresh, sets up the rows the operation needs, then clicks once. A MutationObserver waits for the expected end state (a row count, an id in a given row, a label ending, a selected row) and the clock stops on the next animation frame. Heap is read after a forced garbage collection. Startup is the time from the start of navigation until the app's first button is in the page, from a local server, the median of 40 loads, each in a fresh page, after 2 warm-up loads. Shipped JavaScript is every built .js file, gzipped. Rerun everything with bun run bench at the repo root.

Change one row among 10,000 is the suite chosen for Spar's model, where one store action should end in one text node changing. It is timed twice: to the next frame like the rest, and until the DOM changed, which leaves out the browser's own layout and paint of 10,000 rows. Solid wins it by a wide margin, because it sets one signal. In Spar the store action builds a new array of 10,000 rows and the keyed list is given all of them, so it still walks every key, but it now only compares them and rewrites the one row that changed.
